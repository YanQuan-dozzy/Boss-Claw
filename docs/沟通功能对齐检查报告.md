## 三、未对齐 / 缺失的关键问题

### 问题 1（严重）：沟通对象身份核验完全缺失

- desktop-app 的 `taskState.ts` 定义了 `verify_chat_target` 阶段，`Workbench.tsx` 的 `TRACKED_STAGES` 也包含它，但 `electron/preload/webview.cjs` 的 `startApply()` **从不回传该阶段，也从不核验当前聊天对象**。
- job-claw-main 在 `content-v37.js` 中有完整实现：
  - `ensureExpectedConversation()` — 循环核对目标 HR、会话选中、编辑器就绪；
  - `validateChatContext()` — 会话身份/公司/岗位冲突判定；
  - `assertConversationKey()` — 会话 key 稳定性校验；
  - `boundConversationAssessment()` — 明确冲突即禁止发送；
  - `matchingConversationItem()` — 按 HR 姓名定位左侧会话行。
- 后果：desktop-app 点击「沟通」后直接填文字发送，**违反 AGENTS.md 2.1「目标 HR 或会话明确冲突时：不发送」**。

### 问题 2（严重）：聊天输入框选择器过时

- desktop-app 的 `chatInput` 仅匹配：
  `#chat-input, .chat-input, textarea[placeholder*="聊聊"], .input-area textarea, .chat-message-input textarea`
- BOSS 直聘当前聊天输入框是 **contenteditable div**（`[contenteditable]` / `[data-slate-editor]` / `[data-lexical-editor]` / `[role="textbox"]`），上述选择器**匹配不到**，会直接报「未找到沟通输入框」。
- 且写入方式用 `HTMLTextAreaElement.prototype` 的 value setter，对 contenteditable 元素无效。
- job-claw-main 有 `chatInputScore()` 打分识别 + `setChatText()` 区分 textarea/input 与 contenteditable（用 `execCommand('insertText')` 写入）。

### 问题 3（严重）：文字气泡确认过度宽松

- desktop-app：`document.body.innerText.includes(greeting.slice(0, 12))` —— 仅匹配招呼语**前 12 个字符**，且不排除左侧联系人列表里「其他 HR 会话预览」，易误判为已发送成功。
- job-claw-main：`waitForStableOutgoingGreeting()` 要求**连续 3 次稳定指纹** + 完整招呼语匹配 + `transcriptGeometry()` 几何校验（排除其他 HR 预览、排除「竞争者PK/查看详细分析」等干扰文本）。
- 后果：**违反 AGENTS.md 2.1「未确认右侧聊天文字气泡时：不计成功、不跳下一岗位」**。

### 问题 4（中等）：沟通入口 / 弹窗 / 域名交接不完整

- desktop-app 的 `chatButton` 仅匹配「立即沟通」类（`a.op-btn-chat, .btn-chat, .op-btn.chat, .btn-start-chat, button:contains(沟通)`）。
- job-claw-main 额外处理：
  - `communicateButton()` 识别「立即沟通 / 继续沟通 / 打招呼 / 去沟通」；
  - `dialogConfirmButton()` 处理「继续沟通 / 确认沟通 / 去沟通」弹窗；
  - `enterChat()` 处理 `app.zhipin.com` 域名交接、移除 `target="_blank"`、多轮重试建立沟通关系。
- 缺这些会导致「继续沟通」「打招呼」型入口无法进入聊天页。

### 问题 5（中等）：招呼语最小长度校验缺失

- job-claw-main `sendGreeting()`：`safeGreeting.length < 8` 直接抛错拒绝发送。
- desktop-app webview 侧无此校验（仅 Workbench 的 onApprove 有非空检查，但无长度下限）。

### 问题 6（中等）：外部网申检测失效

- job-claw-main `externalApplicationInfo()` 检测「立即网申 / 去网申 / 立即申请」并标记为 `external_application`。
- desktop-app `priority.ts` 有 `-6000` 惩罚逻辑，但 `applicationMode` 字段**无任何代码赋值**（webview 未检测），等于这条安全规则实际不生效。

### 问题 7（低）：会话锁 / 防重复投递未接线

- `conversationIdentity.ts` 的三个函数已移植但 grep 全项目**无任何调用方**，`deriveConversationReservationKey` / `sameRecruiterReservation` 的「防重复投递 / 防发错人」锁实际未启用。

## 四、修复建议（按优先级）

1. **【P0】补齐沟通对象核验**：在 webview.cjs 中移植 `ensureExpectedConversation` 的核心逻辑（识别左侧会话、核对 HR 姓名、判定公司/岗位冲突），在 `startApply` 的 `open_chat` 后回传 `verify_chat_target` 阶段与核验结果；不匹配即 `failed` 暂停。
2. **【P0】重写输入框定位与写入**：采用打分式 `chatInput` 识别（含 contenteditable/slate/lexical/role=textbox），并区分 textarea 与 contenteditable 的写入路径。
3. **【P0】收紧文字气泡确认**：移植 `waitForStableOutgoingGreeting` 的稳定指纹 + 完整招呼语匹配 + 几何校验，替代 `slice(0,12)` 的宽松匹配。
4. **【P1】补齐沟通入口**：增加「继续沟通/打招呼」入口识别、弹窗确认、app.zhipin.com 域名交接。
5. **【P1】加招呼语长度下限**（`< 8` 字拒绝发送）。
6. **【P1】实现外部网申检测**，为 `applicationMode` 赋值，让 `-6000` 惩罚生效。
7. **【P2】接线会话锁**：在投递前用 `deriveConversationReservationKey` / `sameRecruiterReservation` 做防重复投递。
